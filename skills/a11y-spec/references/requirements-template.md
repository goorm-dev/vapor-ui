# 요구사항 문서 템플릿 (Notion 발행용)

`report-template.md`가 **설계 입력**(SC 단위, 책임 3분할, 실측 근거)이라면 이 문서는 **공유용
요구사항 목록**이다. 같은 실측에서 나오지만 재단 축이 다르다 — SC가 아니라 **요구사항 문장 하나**가
행이고, 독자는 팀과 소비자다.

정본 양식: <https://app.notion.com/p/goorm/Dialog-3b44e6997fb081bda6fddfbfa3f1d5da>

이 문서는 6단계 리포트를 **대체하지 않는다.** 리포트가 먼저 있어야 이 문서를 쓸 수 있다 —
근거 칸에 적을 실측이 리포트에만 있다.

---

## 리포트 → 요구사항 문서 변환

### 섹션 매핑

| 리포트 섹션                    | 요구사항 문서 섹션            |
| ------------------------------ | ----------------------------- |
| 2. 컴포넌트 책임               | 디자인 시스템이 보장하는 요구사항 |
| 3. 공동 책임 + 4. 통합자 책임  | 소비자가 충족해야 하는 요구사항 |
| 5. 제외                        | **싣지 않는다** — 제외는 판정 근거지 요구사항이 아니다 |
| 6. 설계 결정                   | **싣지 않는다** — 미결 사항은 발행 문서에 넣지 않는다 |
| 1. 성질                        | 헤더 불릿의 `대상 패턴`으로만 압축 |

### Base UI 열 어휘 매핑

리포트의 네 표기를 이 문서의 여섯 어휘로 옮긴다. **정보를 잃지 않게 뒤에 설명을 붙인다.**

| 리포트 표기   | Base UI 열              | 붙일 설명                                     |
| ------------- | ----------------------- | --------------------------------------------- |
| `위임`        | `지원`                  | 없음 (근거는 리포트에 있다)                   |
| `위임` (수단이 규범과 다름) | `지원 (다른 방식)` | **필수** — 무엇으로 대신했는지 (예: `aria-modal` 대신 형제 `aria-hidden`) |
| `조건부 위임` | `부분`                  | **필수** — 어느 prop 조합에서만인지            |
| `자체 구현`   | `미지원`                | 상류가 unstyled라서인지, 기능을 안 해서인지 구분 |
| 공동 책임의 통로 | `슬롯 제공`          | 어느 파트·prop이 통로인지 (예: `Dialog.Title`이 `aria-labelledby`를 연결) |
| `미확인`      | `DOM 확인 불가`         | 브라우저로 판정 불가인 경우만. **실측을 안 했을 뿐이면 실측하고 온다** |

> ⚠️ 이 문서의 `근거` 칸은 APG·MDN을 **직접 인용한다.** 리포트의 근거 위계(APG는 각주만)와
> 어긋나는 지점이니 헷갈리지 마라 — 리포트는 준수 판정 근거를 다루고, 이 문서는 요구사항의
> 출처를 밝힌다. WCAG SC가 있는 요구사항은 SC를 쓰고, APG·MDN에만 있는 요구사항은 그것을 쓴다.

## 카테고리와 슬러그

요구사항은 `### <카테고리>` 아래 `### <슬러그>`로 묶는다. 카테고리는 **AT가 무엇을 얻는가**로
나눈다 — SC 번호순이나 원칙순이 아니다.

| 카테고리           | 담는 것                                     |
| ------------------ | ------------------------------------------- |
| `role`             | 역할 부여                                   |
| `state`            | 상태 속성·배경 비활성화                     |
| `structure`        | 관계·자손 구조·필수 자식                    |
| `name-description` | 접근 가능한 이름·설명                       |
| `focus`            | 포커스 이동·복귀·표시·가려짐                |
| `keyboard`         | 키 인터랙션                                 |
| `contrast`         | 명도 대비                                   |
| `presentation`     | 확대·텍스트 간격·리플로·방향                |
| `target`           | 타깃 크기·포인터                            |

카테고리가 비면 그 `###`를 쓰지 않는다 — 이 문서는 비교용이 아니라 발행용이라 빈 칸을 남기지
않는다. (리포트와 반대다.)

슬러그는 kebab-case로 **요구사항 문장을 압축**한다: `dialog-role`, `focus-returns-on-close`,
`keyboard-escape-closes`, `target-size-minimum`. 컴포넌트 이름을 접두사로 붙이지 않는다.

## 문장 규칙

- `요구사항`·`이유`는 **영어**로 쓴다. 규범 원문 어휘를 그대로 실어야 대조가 되기 때문이다.
- `요구사항`은 `must`/`may`를 쓴다 — 규범 강도가 문장에 드러나게. `should`는 쓰지 않는다.
- `이유`는 **누가 무엇을 못 하게 되는지** 한 문장. "접근성을 위해" 같은 순환 설명 금지.
- 표 라벨(`요구사항`/`근거`/`이유`/`Base UI`)과 `Base UI` 칸 설명은 **한글**이다.
- 하나의 요구사항이 두 카테고리에 걸치면 **쪼갠다.** 한 행에 두 요구가 들어가면 소비자가 절반만
  지키고 지켰다고 본다.

## 헤더 불릿 규칙

- `항목 수`의 두 숫자 합이 본문 표 개수와 **정확히** 같아야 한다. 안 맞으면 어느 요구사항이
  섹션에서 빠진 것이다.
- `Base UI 구현`의 여섯 숫자 합도 표 개수와 같다. 이 두 줄이 이 문서의 유일한 자기 검산이다.

## 발행

파일은 `reports/<component>-requirements.md`에 쓴다. Notion에 올릴 때는 `프로덕트 문서`
데이터베이스에 `유형: 개발 가이드`, `해시태그: Vapor Components`로 넣는다 — 정본 Dialog 문서와
같은 속성이어야 같은 뷰에 모인다.

Notion 표는 마크다운 표를 그대로 옮기면 된다. 첫 행이 빈 헤더 행(`| | |`)인 것은 정본 양식
그대로다 — 라벨-값 2열 표에 헤더가 필요 없어서다.
