# 리포트 템플릿

산출물은 이 문서 **한 부**다. 설계 입력이면서 Notion 발행용이다. 모든 컴포넌트가 이 골격을
그대로 따른다.

**행 하나 = 요구사항 문장 하나.** SC가 행이 아니다 — SC 하나가 요구사항 여러 개로 쪼개진다.

정본 양식은 사내 Notion의 Dialog 문서를 따른다. **링크는 이 저장소에 적지 않는다 — 공개
저장소다.**

## 판정 어휘

`verify.md`가 이 어휘로 직접 판정한다 — `지원` / `지원 (다른 방식)` / `부분` / `명세 위임` /
`미지원` / `확인 불가`. 뜻과 함께 적을 것은 `verify.md` § 판정 어휘가 소유한다.

구획이 정하는 어휘가 둘 더 있다.

| 어휘        | 붙는 곳         | 함께 적을 것                                                              |
| ----------- | --------------- | ------------------------------------------------------------------------- |
| `슬롯 제공` | `3. 공동(통로)` | 어느 파트·prop이 통로인가 (예: `Dialog.Title`이 `aria-labelledby`를 연결) |
| `해당 없음` | `4. 소비자`     | 소비자 몫이라 기반 구현체가 관여하지 않는다                               |

여덟 어휘가 검산 둘째 줄의 항목이다.

## 근거 어휘 — 이중이다

- **WCAG SC가 있으면 SC를 쓴다.** `WCAG 2.2 SC 4.1.2` / `KWCAG 8.2.1`
- **APG·MDN에만 있는 행위는 그것을 쓰고 「정보성」 라벨을 붙인다.** `APG Dialog 패턴 (정보성)`
  / `MDN role=progressbar (정보성)`

APG는 저작 실무 가이드이고 명세가 아니다. KWCAG 8.2.1이 요구하는 것은 **플랫폼 접근성 API
지원**이다 — 네이티브 HTML 의미로 충분하면 그것이 근거고, WAI-ARIA는 실제 사용한 구현에서만
근거로 연결한다. 라벨이 규범과 권고를 가른다.

## 카테고리와 슬러그

요구사항은 `### <카테고리>` 아래 `### <슬러그>`로 묶는다. 카테고리는 **최종 사용자가 무엇을
얻는가**로 나눈다.

| 카테고리           | 담는 것                      |
| ------------------ | ---------------------------- |
| `role`             | 역할 부여                    |
| `state`            | 상태 속성·배경 비활성화      |
| `structure`        | 관계·자손 구조·필수 자식     |
| `name-description` | 접근 가능한 이름·설명        |
| `focus`            | 포커스 이동·복귀·표시·가려짐 |
| `keyboard`         | 키 인터랙션                  |
| `contrast`         | 명도 대비                    |
| `presentation`     | 확대·텍스트 간격·리플로·방향 |
| `target`           | 타깃 크기·포인터             |

내용이 있는 카테고리만 쓴다. 구획마다 3~5개가 나타난다.

슬러그는 kebab-case로 **요구사항 문장을 압축**한다: `dialog-role`, `focus-returns-on-close`,
`keyboard-escape-closes`, `target-size-minimum`. 컴포넌트 이름은 접두사에서 뺀다.

## 문장 규칙

- `요구사항`·`이유`는 **영어**로 쓴다. 규범 원문 어휘를 그대로 실어야 대조가 된다.
- `요구사항`은 `must`/`may`를 쓴다 — 규범 강도가 문장에 드러나게.
- `이유`는 **누가 무엇을 못 하게 되는지** 한 문장으로 쓴다.
- 표 라벨과 `기반 구현체` 칸 설명은 **한글**이다.
- 요구사항 하나가 두 카테고리에 걸치면 **쪼갠다.** 한 행에 두 요구가 들어가면 소비자가 절반만
  지키고 지켰다고 본다.

## 공동 SC는 두 행으로 쪼갠다

공동 SC는 문장 두 개다. vapor 쪽 문장은 `3. 공동(통로)`에, 소비자 쪽 문장은 `4. 소비자`에 각각
한 행으로 싣고, 두 행은 **슬러그 접두사를 공유**해 짝임을 보인다.

보기 — `1.1.1` (icon):

- `3. 공동(통로)` / `icon-name-slot` — The component must accept an accessible name via `aria-label`.
- `4. 소비자` / `icon-name-content` — The consumer must provide a name that states the icon's purpose.

각 행의 `짝` 라벨에 상대 슬러그를 적는다. 한 행에 두 문장을 담으면 검산 첫째 줄이 깨진다.

## 검산 3줄

이 문서의 자기 검증이다.

| 줄            | 식                                        | 무엇을 잡나          |
| ------------- | ----------------------------------------- | -------------------- |
| `요구사항 수` | `a + b + c + d` = 본문 표 개수            | 구획 배정 누락       |
| `위임 판정`   | 여덟 숫자의 합 = 본문 표 개수             | 판정 어휘 누락       |
| `SC 판정`     | `60 = 채택 + 제외`, 제외 수 = 부록 C 행수 | **필터에서 빠진 SC** |

앞 두 줄은 **이미 실린 것만** 센다. `1.4.12`를 필터에서 놓치면 표가 하나 줄고 헤더 숫자도 하나
줄어 두 식이 그대로 맞는다. 셋째 줄만이 실리지 않은 것을 센다 — 기반 구현체를 먼저 보는 절차의
편향(base-ui가 하는 것만 요구사항이 되는)이 그 형태로 나타난다.

채택 SC 수와 `요구사항 수`의 합은 **다르다** — SC 하나가 요구사항 여럿으로 쪼개진다(Dialog면
SC 27건이 요구사항 40개 남짓). 두 숫자는 각자 자기 식만 만족한다.

## 섹션별 작성 규칙

### 헤더

`증거` 줄에 **prop 설정과 뷰포트를 적는다.** 같은 컴포넌트도 prop에 따라 판정이 갈리므로, 어느
설정에서 잰 값인지가 증거의 일부다.

`기반 구현체`가 `없음 — 커스텀 구현`이면 **확인 날짜를 적는다.** 그것은 관측이 아니라 사용자가
2단계 게이트에서 내린 결정이다.

### 1~2 구획

`기반 구현체` 칸에 **관측한 값을 그대로** 적는다 — 속성값, 계산된 대비비, 픽셀 수치, 포커스가 간
요소의 텍스트. "충족함" 같은 요약은 증거가 아니다.

기반 구현체가 unstyled면 **시각 축**의 컴포넌트 몫은 예외 없이 `2. vapor 자체 구현`이다(목록은
`sc-map.md`가 소유한다). 데모에서 잰 값은 기준선으로만 적는다.

### 3 구획

각 행이 **prop 하나로 번역돼야 한다.** "`aria-label`을 받을 수 있게"까지 적고, 필수로 강제할지는
부록 D로 올린다.

### 부록 A·B

A·B가 근거, C·D가 그 결과다. **부록 A의 `X` 행이 부록 C의 근거다** — 성질이 안 붙은 이유가 SC가
빠진 이유다.

부록 B의 각 행에 **요구사항 슬러그를 역참조로 적는다.** 슬러그가 빈 칸은 요구사항으로 번역되지
않은 행위이므로 사유를 적는다.

## 발행

파일은 `reports/<component>.md`에 쓴다. Notion에 올릴 때는 `프로덕트 문서` 데이터베이스에
`유형: 개발 가이드`, `해시태그: Vapor Components`로 넣는다 — 정본 Dialog 문서와 같은 속성이어야
같은 뷰에 모인다.

Notion 표는 마크다운 표를 그대로 옮긴다. 첫 행이 빈 헤더 행(`| | |`)인 것은 정본 양식 그대로다 —
라벨-값 2열 표에 헤더가 필요 없어서다.
